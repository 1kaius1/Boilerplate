# Ansible Vault: a complete walkthrough

This guide assumes you have never used Ansible Vault before. Every section names
the exact command to run, what you should see if it works, and what it looks like
when it doesn't. Commands are shown as run from this project's root directory.

> **A note on `project` / `vault_pass_project.txt`:** every command below uses these
> as concrete, copy-pasteable examples - they're just the default label and
> filename in [`ansible.cfg.example`](../ansible.cfg.example) (see the comment
> there), not a fixed requirement. No playbook hardcodes this name; they only ever
> read whatever `vault_identity_list` says in `ansible.cfg`. If you personalize the
> label/filename, use the same one consistently and substitute it everywhere
> `project`/`vault_pass_project.txt` appears below. (For a *per-vault* identity
> split instead of one shared password, see section 12.)

## 1. What Vault is, and why this template uses it this way

Ansible Vault encrypts a file (or a single value) at rest using AES256. Ansible
decrypts it transparently in memory whenever a playbook runs, as long as it has the
right password - nothing about how you write a task changes. A task that needs a
password just references `{{ vault_db_password }}` like any other variable.

Secrets are split into two files:

- `vars.yaml` - plaintext, committed to git. Holds normal config plus *references*
  to secrets, e.g. `db_password: "{{ vault_db_password }}"`.
- `vault.yaml` - fully encrypted, and **gitignored** - not committed at all. Holds
  the actual values.

The encrypted file is kept out of a public repo even as ciphertext: its first line,
`$ANSIBLE_VAULT;1.2;AES256;<vault-id>`, is cleartext, and the `<vault-id>` label
there names a real credential. Only `vault.yaml.example` (plaintext placeholders,
the variable references) is committed. Recovery of a real `vault.yaml` is via the
vault password + `ansible-vault create` from the `.example`, or an out-of-band copy
of the file - **not** git history. Losing the vault password means losing access to
everything it protects, so section 2 matters more than it looks.

A project typically has one `vault.yaml` per meaningful secret scope - e.g. one for
a shared/common credential, one per role or environment that needs its own secrets.
Some are generated by a playbook (see section 4's note); most are hand-created.
Unless you've split them (section 12), all of a project's vault files can share one
vault password (vault-id `project` in the examples).

## 2. One-time setup: your vault password file

The vault password itself is **not** a file you commit. It lives outside the repo,
and Ansible is told where to find it.

```bash
mkdir -p ~/.ansible
chmod 700 ~/.ansible
openssl rand -base64 32 > ~/.ansible/vault_pass_project.txt
chmod 600 ~/.ansible/vault_pass_project.txt
```

**Expected result:** no output from any of these commands. Check it worked:

```bash
$ cat ~/.ansible/vault_pass_project.txt
Xk3p9...   (a random base64 string)
$ ls -l ~/.ansible/vault_pass_project.txt
-rw------- 1 you you 45 Sep  1 12:00 /home/you/.ansible/vault_pass_project.txt
```

The `-rw-------` (mode 600) matters - anyone who can read this file can decrypt
every secret it protects.

**This is the single most important file in this whole setup.** If you lose it,
every `vault.yaml` it encrypts becomes permanently unreadable - there is no
recovery. Back it up somewhere durable (a password manager entry is ideal) before
going further. If this project has its own vault-recovery runbook, link it here -
there is no way to recover a lost vault password otherwise.

## 3. How the password file is wired to Ansible

`ansible.cfg` (copied from the committed [`ansible.cfg.example`](../ansible.cfg.example))
contains:

```ini
[defaults]
vault_identity_list = project@~/.ansible/vault_pass_project.txt
```

This tells Ansible: "there's a vault identity labeled `project`, and its password
lives at that path." Any `ansible-playbook` or `ansible-vault` command run from this
directory picks this up automatically - no `--ask-vault-pass` flag needed.

**What it looks like if the file is missing:**
```
$ ansible-playbook create-example.yaml
ERROR! Attempting to decrypt but no vault secrets found
```

**What it looks like if the file exists but has the wrong permissions on some
systems (rare, but shows as):**
```
ERROR! Unable to read vault password file '/home/you/.ansible/vault_pass_project.txt': [Errno 13] Permission denied
```
Fix: `chmod 600 ~/.ansible/vault_pass_project.txt`.

## 4. Creating a new vaulted file

Some vault files may be generated for you - if a playbook runs `ansible-vault
create` internally as part of provisioning a credential, document that here rather
than creating it by hand. Otherwise, create one yourself, using its
`vault.yaml.example` as the reference for which variables it needs:

```bash
ansible-vault create group_vars/<group>/vault.yaml
```

No `--vault-id` flag needed - with one identity configured in `vault_identity_list`
(section 3), Ansible unambiguously uses it, reading the password straight from
`~/.ansible/vault_pass_project.txt`. (You'd need `--vault-id`/`--encrypt-vault-id`
once more than one identity is configured - see section 12.)

**What happens:** no password prompt at all (it's read from the file silently),
then your `$EDITOR` opens an empty file. Type the real content, matching the
`vault.yaml.example`, e.g.:

```yaml
---
vault_db_password: "a-real-generated-password"
vault_admin_password: "another-real-generated-password"
```

**Watch for app-specific format constraints.** Some applications reject otherwise-
valid secret encodings - e.g. a value that must be URL-safe base64 will fail
validation if generated as hex or padded base64 instead. The authoritative note for
any such field belongs in that project's own `vault.yaml.example`. The vault
password itself (section 2) has no such constraint.

Save and close the editor. Ansible encrypts the file the moment the editor exits.

**Confirm it worked:**
```bash
$ head -c 15 group_vars/<group>/vault.yaml
$ANSIBLE_VAULT;1
```
If you see that header, the file is encrypted. If you instead see plain YAML text,
encryption did not happen - do not commit it; delete and retry.

## 5. Editing an existing vault file

```bash
ansible-vault edit group_vars/<group>/vault.yaml
```

**What happens:** Ansible decrypts the file to a temporary location, opens it in
`$EDITOR`, and re-encrypts it the moment you save and close - silently, with no
output at all if it succeeds. That silence is normal; a command that prints nothing
and returns you to the prompt means it worked.

**What failure looks like** (wrong vault password configured, or file corrupted):
```
ERROR! Decryption failed (no vault secrets were found that could decrypt) on group_vars/<group>/vault.yaml
```

## 6. Viewing without editing

```bash
$ ansible-vault view group_vars/<group>/vault.yaml
---
vault_db_password: "a-real-generated-password"
```
Prints the decrypted content to your terminal and exits - the file on disk is
untouched. Use this to sanity-check a file before a real run (see section 10).

## 7. Encrypting/decrypting an existing plaintext file in place

If you ever end up with a plaintext file that should have been encrypted (e.g. you
`cp`'d `vault.yaml.example` to `vault.yaml` and filled in real values without using
`ansible-vault create`):

```bash
ansible-vault encrypt group_vars/<group>/vault.yaml
```

The reverse (rarely needed - mainly for one-off inspection with a tool that can't
call `ansible-vault` itself):
```bash
ansible-vault decrypt group_vars/<group>/vault.yaml
```
**Never leave a file decrypted and walk away from it** - re-encrypt immediately
after you're done, and never `git add` a file in a decrypted state (check with the
`head -c 15` trick from section 4 before committing anything under a `vault.yaml`
name).

## 8. Encrypting a single value inline

For a one-off secret you want inline in an otherwise-plaintext file, rather than a
whole separate vault file:

```bash
$ ansible-vault encrypt_string 'my-secret-value' --name 'some_var_name'
some_var_name: !vault |
          $ANSIBLE_VAULT;1.2;AES256;project
          66386439653...
```
Paste that whole `some_var_name: !vault |` block directly into a plaintext YAML
file. Only use this pattern if this project has deliberately chosen it over
whole-file vaulting - it's useful to recognize either way.

## 9. Running a playbook non-interactively

```bash
$ ansible-playbook create-example.yaml
PLAY [...] *******************************************
...
```
No password prompt appears - `vault_identity_list` in `ansible.cfg` handles it
silently. This is what a normal run looks like.

**To see the alternative** (so you recognize it if `ansible.cfg` ever gets
misconfigured), comment out the `vault_identity_list` line and try again:
```
$ ansible-playbook create-example.yaml
Vault password (project):
```
It's now waiting on you to type the password interactively. Ctrl+C out, uncomment
the line, and don't run it this way normally - a playbook waiting on a password
prompt can't run from cron or unattended.

## 10. Sanity-checking before a real run

Before running against real infrastructure:
```bash
ansible-vault view group_vars/<group>/vault.yaml
ansible-playbook create-example.yaml --syntax-check
```
If the `view` command prints readable YAML and `--syntax-check` prints
`playbook: create-example.yaml` with no errors, you're ready.

## 11. Rotating the vault password

If you suspect `~/.ansible/vault_pass_project.txt` has been exposed, rotate it -
`rekey` every file it protects:

```bash
openssl rand -base64 32 > ~/.ansible/vault_pass_project_new.txt
chmod 600 ~/.ansible/vault_pass_project_new.txt

for f in group_vars/<group>/vault.yaml \
         group_vars/<other_group>/vault.yaml ; do
  ansible-vault rekey \
    --vault-id project@~/.ansible/vault_pass_project.txt \
    --new-vault-id project@~/.ansible/vault_pass_project_new.txt \
    "$f"
done
```
Then replace the old file with the new one:
```bash
shred -u ~/.ansible/vault_pass_project.txt
mv ~/.ansible/vault_pass_project_new.txt ~/.ansible/vault_pass_project.txt
```
`ansible.cfg` already points at `vault_pass_project.txt` by name, so no config
change is needed once the rename above is done - just make sure every
machine/user that runs these playbooks gets the new password file, since the old
one no longer works.

## 12. Vault-ID strategy - one identity, or several

The examples use one vault-id, `project`. As you add a new environment or a second
credential scope, you don't need to touch existing vault files - just add a second
identity:

```ini
# ansible.cfg
vault_identity_list = project@~/.ansible/vault_pass_project.txt, staging@~/.ansible/vault_pass_staging.txt
```

Then create that scope's own vault file under the new label. With two identities
configured, Ansible can no longer guess which one to encrypt *new* content with, so
`create`/`encrypt` need `--encrypt-vault-id` to say which (a bare label, not
`label@source` - that form is only for `--vault-id`):
```bash
ansible-vault create --encrypt-vault-id staging group_vars/staging/vault.yaml
```

This only matters for creating/encrypting. **Reading** an already-encrypted file
(`view`/`edit`/decrypting for a playbook run) needs no flag at all either way -
Ansible tries each configured identity's password against the file and matches by
the label stamped in its ciphertext header (`$ANSIBLE_VAULT;1.2;AES256;staging`), so
both identities coexist transparently for everything except creating something new.

### Splitting by vault file, not just by environment

The same mechanism gives you **one password per `vault.yaml`** - so a leaked or
lost password only burns that file's secrets, not every vault in the project. Pick
a scheme (one identity per role, or per environment), name the identities after
their *purpose* (the label lands in the cleartext header - don't put a network/host
name there), and list them all in `vault_identity_list`:

```ini
vault_identity_list = shared@<vault-dir>/shared, app@<vault-dir>/app
```

Each `vault.yaml` is then created once under its label:
```bash
ansible-vault create --encrypt-vault-id app group_vars/app/vault.yaml
```
If a playbook generates a vault file for you (see section 4), and more than one
identity is configured, it will need to be told which label to encrypt with -
document that playbook's own convention for this (e.g. an extra-var) here.

### The password files

They can live anywhere `ansible.cfg` can reach. Pick a durable location **outside
`~/.ansible/`** - a stray cleanup of Ansible's state directory shouldn't take your
keys with it - and **back up each one the moment you create it**: the encrypted
`vault.yaml`s are gitignored, so a lost password means that ciphertext is gone for
good, no git history to fall back on.

A `vault_identity_list` entry may also point at an **executable script** instead of
a flat file - Ansible runs it and reads the password from its stdout. Source it
from `pass show ...`, `gpg -d ...`, `bw get password ...`, a keyring, etc., and
there is no standing plaintext secret on disk.

## 13. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `ERROR! Decryption failed (no vault secrets were found that could decrypt)` | Wrong password, or the file's ciphertext is corrupted | Confirm the right vault-id/password file is configured; if the file is genuinely corrupted, restore it from your out-of-band backup or re-create it from `vault.yaml.example` (the real `vault.yaml` is gitignored - there is no earlier commit to restore) |
| `ERROR! Attempting to decrypt but no vault secrets found` | `vault_identity_list` isn't set, or you're running from a directory without the right `ansible.cfg` | Check you're in this project's root and that `ansible.cfg` has the `vault_identity_list` line |
| A command prompts interactively for the vault password (`Vault password (...):`) even though `vault_identity_list` is configured | Ansible only reads `ansible.cfg` from the **current working directory** - never a parent or sibling | `cd` into the directory whose `ansible.cfg` you want before running `ansible-vault`/`ansible-playbook`, or pass `--vault-id`/set `ANSIBLE_CONFIG` explicitly |
| `ansible-vault requires the cryptography library in order to function` | Not a vault problem - this is the system (or another) Ansible install running, not this project's venv | Use the venv explicitly, e.g. `.venv/bin/ansible-vault view <path>`, or `source .venv/bin/activate` first - see this project's own toolchain documentation |
| `Unable to read vault password file: Permission denied` | Wrong file permissions | `chmod 600 ~/.ansible/vault_pass_project.txt` |
| A `vault.yaml` was `git add -f`'d while **decrypted** | Someone ran `ansible-vault decrypt`, then force-added past the gitignore before re-encrypting | This is a real incident, not a formatting fix: the secret is now in git in plaintext. Rotate every value in that file immediately, re-encrypt, and commit the removal. Rewriting history to drop the old blob does not fully solve this - treat the exposed secret as burned. (The `vault.yaml` gitignore normally prevents this - never `-f` past it.) |

## 14. Cheat sheet

```bash
# One-time setup
openssl rand -base64 32 > ~/.ansible/vault_pass_project.txt && chmod 600 ~/.ansible/vault_pass_project.txt

# Create a new vault file (no --vault-id needed with one identity configured)
ansible-vault create <path>

# Edit
ansible-vault edit <path>

# View (read-only)
ansible-vault view <path>

# Encrypt an existing plaintext file
ansible-vault encrypt <path>

# Decrypt in place (avoid leaving it this way)
ansible-vault decrypt <path>

# Encrypt a single value inline
ansible-vault encrypt_string 'value' --name var_name

# Once a SECOND identity is configured (section 12), create/encrypt need
# --encrypt-vault-id to say which one - reading never does:
ansible-vault create --encrypt-vault-id staging <path>

# Rotate the vault password
ansible-vault rekey --vault-id project@<old-file> --new-vault-id project@<new-file> <path>

# Run a playbook (no prompt, if ansible.cfg is set up)
ansible-playbook create-example.yaml
```
